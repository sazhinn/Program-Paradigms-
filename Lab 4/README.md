# Лабораторная работа 4. Структурное программирование и модульная организация

**Индивидуальный вариант:** 1 - буквенная оценка A, B, C, D, F.

## Структура
```
lab4_project/
├── university_rating/
│   ├── __init__.py       публичный интерфейс пакета
│   ├── validation.py     проверка данных
│   ├── calculations.py   среднее, статус, буквенная оценка (расширение)
│   ├── rating.py         результат студента и сортировка
│   ├── report.py         текстовый отчет
│   └── main.py           точка входа
└── tests/test_rating.py  автоматические тесты
```
Зависимости: main -> report, rating; rating -> calculations, validation. Циклов нет.

## Запуск (из папки lab4_project)
```bash
python -m university_rating.main
python -m unittest discover -s tests -v
```
Ожидаемый вывод:
```
Рейтинг группы
1. Amina: 86.33 — допущен, оценка B
2. Dias: 48.33 — не допущен, оценка F
3. Mira: — — нет данных, оценка —
```

## Индивидуальное расширение (вариант 1)
Функция `determine_letter(average)` в `calculations.py`: 90+ это A, 75+ B, 60+ C, 50+ D, ниже 50 F, для пустого списка None. Буква добавляется в результат студента (`rating.py`) и выводится в отчете (`report.py`). Для нее написано 2 теста.

## Вывод
Каждый модуль отвечает за одно дело: проверка, расчет, рейтинг, отчет, запуск. Зависимости идут в одну сторону, от main к расчетным модулям, поэтому формат отчета можно менять, не трогая расчеты. Расширение с буквенной оценкой добавилось в calculations, rating и report без правок остальных модулей.

## Ответы на контрольные вопросы
1. Последовательность, выбор (ветвление), повторение (цикл).
2. Модуль это один файл .py, пакет это папка с модулями и `__init__.py`.
3. Высокая связность: в модуле собраны функции одной задачи. Слабое зацепление: модули зависят друг от друга минимально, через небольшой интерфейс.
4. Чтобы расчеты можно было использовать и тестировать отдельно от вывода (в консоль, GUI, веб).
5. Чтобы код запускался только при прямом запуске файла, а не при импорте.
6. Непонятно, откуда пришли имена, возможны конфликты имен.
7. Модули импортируют друг друга по кругу (A импортирует B, B импортирует A). Лечится переносом общего кода в третий модуль или изменением направления зависимости.
8. Чтобы предметные модули можно было использовать и тестировать без интерфейса, а изменение интерфейса не ломало расчеты.
9. Сравнить входные данные с копией до вызова (тест `test_source_is_not_changed`).
10. Модуль `report.py`.
